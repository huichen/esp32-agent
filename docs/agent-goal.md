# A goal on the board: an autonomous loop

Status: contract. This document specifies the goal loop; `ROADMAP.md` records whether
the implementation has landed and been measured on hardware.

A turn is reactive — a user message, a scheduled prompt or a sensor rule arrives and the
agent answers it. A **goal** makes the board work towards one objective on its own:
you state what you want, and the board iterates until it is done, it is stuck, or its
iteration budget is spent.

The loop is deliberately rough, in the manner of
[gnhf](https://github.com/kunchenguid/gnhf): one small step per iteration, its result
written down as a note, and the next iteration starting from those notes. There is no
planning tree, no separate judge and no sub-agents — the agent that takes the step is
the agent that decides, at the end of that step, whether the objective has been reached.

```
objective
  -> iteration prompt (objective + notes + "iteration N of M")
  -> the existing agent turn (bounded by agent.max_steps)
  -> classify the reply: MET / BLOCKED / CONTINUE
  -> CONTINUE: append a one-line note, start the next iteration
  -> stop on met / blocked / exhausted / stopped
```

## 1. The iteration prompt

Each iteration is an ordinary agent turn whose user message is generated by the goal,
not typed by a person. The prompt carries:

- the objective;
- every stored note, numbered, oldest first;
- the iteration number and the cap;
- the instruction to take **one** concrete step, to write the result as **one line**,
  and to print a line containing `GOAL MET` when the objective is achieved or
  `GOAL BLOCKED` when it cannot proceed.

The prompt is bounded (roughly 1200 characters even with a full note list), because it
is rebuilt from NVS on every iteration and the notes are small by construction.

## 2. Classification

`classify(reply)` reads the **whole** reply, case-insensitively:

| Reply contains | Result |
|---|---|
| `GOAL MET` | `Met` |
| `GOAL BLOCKED` (and not `GOAL MET`) | `Blocked` |
| anything else | `Continue` |

The marker is read from the assistant's final text for that iteration — not from a tool
result it merely relayed, and not from the notes. It is the model's own statement about
the objective, and a reply without it means "not yet".

## 3. The rules

Constants: `DEFAULT_MAX_ITERATIONS = 10`, `NOTE_MAX_CHARS = 240`, `NOTE_CAP = 24`,
`MAX_CONSECUTIVE_FAILURES = 3`. `max_iterations` is clamped to 1–100 on creation and on
load.

1. **Only a running goal has a prompt.** A goal in any other status produces none, so a
   finished goal never queues another turn.
2. **A completed iteration advances the count.** `iteration` counts completed
   iterations, successful or not. A failed iteration consumes budget too — the budget is
   a limit on effort, not on success.
3. **Every iteration leaves one note.** The first line of the reply, trimmed and
   truncated to `NOTE_MAX_CHARS` on a character boundary; the oldest note is dropped
   past `NOTE_CAP`. A note is what the next iteration reads; it is not a log.
4. **A step forward resets the failure count.** Successive failures are counted only
   while they are successive.
5. **Three consecutive failures abort.** The third failed iteration in a row sets
   `Blocked` with a stop reason naming the count, so a model endpoint that is down cannot
   burn the whole budget.
6. **A failed iteration is written down as `failed: ...`.** The next iteration sees why
   the previous one did not work instead of repeating it blindly.
7. **Hitting the cap ends the goal as `Exhausted`.** Not an error, not a success: the
   board did what it was allowed to do.
8. **A stopped goal never resumes.** `stop` is a decision, not a pause. Restarting means
   posting a new goal.

Statuses: `idle`, `running`, `met`, `blocked`, `exhausted`, `stopped`. Only `running` is
active; the others are terminal apart from `idle`, which is simply "no goal".

## 4. API

The routes live on the existing console router and use the PIN gate the other mutating
routes use.

| Method | Path | Body / result |
|---|---|---|
| `POST` | `/api/goal` | `{"objective": "...", "max_iterations": 10}` — start a goal; `409` if one is already active |
| `GET` | `/api/goal` | the goal, plus `prompt` (the next iteration prompt, or `null`) |
| `POST` | `/api/goal/stop` | `{"reason": "..."}`, optional — `Stopped` |
| `DELETE` | `/api/goal` | back to `idle`, notes cleared |

`GET /api/goal` answers:

```json
{
  "objective": "find the I2C address of the light sensor and read it",
  "status": "running",
  "iteration": 2,
  "max_iterations": 10,
  "failures": 0,
  "notes": ["i2c_scan shows 0x23 and 0x77", "0x23 answers with a BH1750 register"],
  "last_result": "0x23 answers with a BH1750 register",
  "stop_reason": "",
  "updated_ms": 1762778400000,
  "prompt": "Objective: ..."
}
```

`/api/status` gains a `goal` block with `status`, `iteration` and `max_iterations`, so
the console can show a goal without polling the full document.

The portal has a goal card in the agent tab: objective, iteration cap, start, the
status line, the notes newest last, and stop. It refreshes on the poll the panel already
runs.

## 5. Where it lives, and why it is small

- The goal document is one JSON blob in NVS, under the same store that already holds the
  manifest and the configuration. It is written on every state change and read back at
  boot, so a reboot does not lose the objective or the notes.
- `crates/agent-core/src/goal.rs` is the state machine and holds no I/O and no HTTP; the
  agent thread drives it. No new thread and no new server: the scheduler tick that
  already decides whether to queue work also queues the goal turn, and the turn whose
  source is `goal` is the one whose reply is classified.
- A turn from another source — user, schedule, rule — is never classified as an
  iteration, even if it mentions `GOAL MET`.

## 6. What this deliberately is not (versus gnhf)

gnhf runs in a repository on a workstation and leans on git; the board has neither the
disk nor the rollback. The differences are design decisions, not gaps to be filled later:

| gnhf | here |
|---|---|
| Each iteration is a git commit; the history is the memory | Each iteration is a **note** in NVS; there is no repository and no diff |
| A bad step can be reverted | A physical action — a pin moved, a relay switched — **cannot be rolled back**. The loop is written so a wrong step is small and the next note says so |
| Notes and logs can be large | Notes are capped at 240 characters and 24 entries, in RAM and NVS; anything longer must be summarised by the model into the one-line note |
| Several goals, branches, worktrees | **One goal at a time.** A second `POST /api/goal` while one runs is refused with `409` |
| Runs for hours on a workstation | Iterations are bounded by `agent.max_steps` per turn and by `max_iterations` per goal, on a device that also has to serve HTTP |

## 7. Verifying it without an API key

The board serves a scripted model at `POST /selftest/chat/completions`. Point
`agent.base_url` at `http://<board>:80/selftest/chat/completions` (model
`selftest`) and the whole loop runs with no credentials and no external service.

```bash
# 1. start a goal: a real objective, a small cap so the run is short
curl -sS -X POST http://<board>:80/api/goal \
  -H 'Content-Type: application/json' \
  -d '{"objective":"confirm the board answers board_status","max_iterations":2}'

# 2. watch it iterate: status, iteration, notes and failures move on their own
curl -sS http://<board>:80/api/goal

# 3. stop it, or let the cap do it
curl -sS -X POST http://<board>:80/api/goal/stop -d '{"reason":"enough"}' \
  -H 'Content-Type: application/json'
```

What this proves, and what it does not: the scripted model never prints `GOAL MET`, so
the run ends `exhausted` at the cap — which is exactly the path that shows the
machinery. It proves the iteration prompt is built and injected, that the reply is
classified, that one note per iteration is stored and read back, that `iteration` counts
and the cap ends the goal, and that `/api/goal` reflects all of it. Reaching `met`
needs a model that can decide the objective is done, so a scripted reply cannot show it.
The abort path can be shown without one: point `agent.base_url` at an address that
refuses the connection, and each goal turn fails — the third failure in a row ends the
goal as `blocked` with the count in `stop_reason`, which also shows that a failed
iteration consumes budget.

The journal (`GET /api/agent/stream`) shows each goal turn as a normal run with
`source: goal`, so the iterations can be watched while they happen rather than only
afterwards.
